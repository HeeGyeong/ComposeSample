## 2026.09
- New examples added
  - Custom Overscroll — the project had eighteen scroll/gesture examples and zero coverage of overscroll (`overscroll`, `OverscrollEffect` and `LocalOverscrollFactory` all appeared zero times), so the edge of a scroll container was the one part of the gesture pipeline never opened up. The screen contrasts four owners of the delta a list can no longer consume. (a) The platform default that `LocalOverscrollFactory` hands out — stretch on API 31+, glow below. (b) A hand-written `OverscrollEffect` that accumulates the leftover into an `Animatable` and renders it through a `DrawModifierNode` `translate`, so the content slides as one piece instead of stretching. (c) The same effect installed through `LocalOverscrollFactory` for a whole subtree, plus the `null` case — providing null is what removes overscroll entirely, and it is also why `rememberOverscrollEffect()` returns a nullable type. (d) `withoutVisualEffect()` / `withoutEventHandling()`, which split one effect in two so the list handles the events while a header above it does the moving — the way to lift an effect out of the container that would clip it. Reading the foundation 1.11.4 bytecode first settled three things the docs do not spell out: `OverscrollFactory` declares `equals`/`hashCode` as **abstract** members (a CompositionLocal value comparison, so a factory holding a lambda has to be remembered or it recreates the effect on every recomposition); `AndroidEdgeEffectOverscrollFactory` is not public, so "the default effect" can only be obtained through `rememberOverscrollEffect()`; and `LazyColumn` carries its own `overscrollEffect` parameter, which both renders the effect and feeds it events. Every mode runs through one probing decorator that wraps an arbitrary effect and records what `applyToScroll`/`applyToFling` actually receive, so the screen shows the delta, the part the list consumed, the part left over, and the fling velocity before and after — including the fact that nothing reaches the effect at all until the list stops consuming. Not yet verified on a device (none attached during this cycle); build, bytecode probes and the full-recompile warning scan are the evidence so far.
  - Worker Exception Handlers — WorkManager does not take the app down when a worker throws; it logs the throwable, closes the job as FAILED and moves on, so nothing reaches a crash reporter. work-runtime 2.11 opens that blind spot with two `Configuration.Builder` handlers, `setWorkerExecutionExceptionHandler` and `setWorkerInitializationExceptionHandler`, both taking a `Consumer<WorkerExceptionInfo>` (`workerClassName` + `workerParameters` + `throwable`) — the project had zero coverage of either. The screen enqueues four failures and contrasts what each one produces: a worker that throws inside `doWork()`, one that returns `Result.failure()`, one whose constructor throws, and one without a `(Context, WorkerParameters)` constructor. Reading the `WorkerWrapper` and `WorkerFactory` bytecode of 2.11.2 first settled where the calls sit — the initialization handler fires right after the "Could not create Worker" log and the execution handler after "failed because it threw an exception/error", and **both paths then return `Resolution.Failed`, so an escaped exception never becomes a retry**; the default factory walks `Class.forName` → `getDeclaredConstructor` → `newInstance` and rethrows each stage's throwable after logging it, which predicts different throwable shapes per stage. A device run (SM-A725F / Android 13) confirmed all of it and added two details worth the example's existence. (a) Four enqueued failures produce **three** reports: `Result.failure()` is an ordinary return path, so no handler is called, yet its `WorkInfo` state is `FAILED` exactly like the thrown case — the state alone cannot tell "failed" from "died". (b) The constructor case arrives as `InvocationTargetException` whose **`message` is null**, the real text living only in `cause` (`IllegalArgumentException`), while the missing-constructor case arrives as a bare `NoSuchMethodException` carrying the exact signature it searched for (`…MissingConstructorDemoWorker.<init> [class android.content.Context, class androidx.work.WorkerParameters]`) — collecting `throwable.message` alone would silently drop the only useful line for the wrapped case. The run also separated two attempt counters: the handler always sees `workerParameters.runAttemptCount` 0 (the pre-execution value), while the finished `WorkInfo` reports 1 for the two workers that actually ran and 0 for the two that were never constructed, and handlers were invoked on `WM.task-2`/`WM.task-3` rather than the main thread, which is why the screen routes everything through a `StateFlow`. Registration is the other half of the feature and it is app-global: `BaseApplication` now implements `Configuration.Provider`, and the manifest removes work-runtime's own `androidx.startup` `WorkManagerInitializer` with `tools:node="remove"` — without that removal the default initializer wins and the handlers are simply never called, with no error to explain why. The merged manifest was checked to confirm only that initializer is gone while HotSwan, emoji2, lifecycle, OkHttp and ProfileInstaller keep theirs, and every other Configuration value is left at its default so the existing WorkManager example behaves exactly as before
  - Display Cutout & Insets — the project had no insets example at all (`displayCutout`, `safeDrawing`, `safeGestures` and `safeContent` appeared zero times; the nineteen `WindowInsets` hits were scattered usages). The example starts from what the `safe*` insets actually are: not measurements but unions, read straight out of the `WindowInsetsHolder` constructor bytecode of foundation-layout 1.11.4 — `safeDrawing = systemBars ∪ ime ∪ displayCutout`, `safeGestures = tappableElement ∪ mandatorySystemGestures ∪ systemGestures ∪ waterfall`, `safeContent = safeDrawing ∪ safeGestures`, which is where the first trap falls out: **waterfall is not part of safeDrawing**. A device measurement (SM-A725F / Android 13, 1080x2400 @450dpi) then separates the device from the window: the phone does have a punch-hole cutout (`boundingRect=Rect(514, 0 - 566, 86)` per `dumpsys`), yet with `decorFitsSystemWindows=true` every one of the thirteen insets Compose reports is **zero**, status bars included, because the decor has already cut them away. The screen therefore lets you flip `layoutInDisplayCutoutMode` and edge-to-edge in place, and the same device then reports statusBars 0/86/0/0, safeDrawing 0/86/0/135 and safeGestures 0/120/0/135 — the gesture inset being the taller one is why their union, safeContent, follows 120 rather than 86. `WindowInsets.cutoutPath` (new in Compose 1.11; absent in 1.8.2) comes back as `Rect.fromLTRB(514, 0, 566, 86)`, matching the platform bounding rect exactly, and is null until the window opts in. The `displayShape` card corrects an assumption rather than confirming one: it is not API 34-only — core 1.18.0 synthesises a rounded rectangle from `Display.getRealSize()` plus the four `DisplayCompat.getRoundedCorner()` radii (all 90px here), so an API 33 device returns a non-empty path that the platform never provided, and support cannot be judged by a null check because the fallback is `DisplayShapeCompat.EMPTY`, whose `getPath()` hands back a fresh empty Path. Two traps came out of building the screen itself, both caught on the device: a `DisposableEffect` that restored window state was placed inside a list card, and a 40-row measurement showed `onDispose` firing the moment the item scrolls off screen rather than when the screen closes, so the state moved up to the screen root; and the idiomatic `when (this) { is Activity -> ... }` context walk compiles to a JDK 21 `SwitchBootstraps.typeSwitch` invokedynamic that the HotSwan 2.0.0 interpreter in debug builds does not implement, which did not crash but silently emptied the composition (semantics root at 0x0) until it was replaced with `LocalActivity.current`.
  - Sensor-Fusion Compass — the project's first use of the sensor stack (`SensorManager` appeared zero times before this example). Subscribes a single fused `TYPE_ROTATION_VECTOR` sensor and walks the four-step azimuth pipeline (`onSensorChanged` → `getRotationMatrixFromVector`, which returns `void` rather than a success boolean → `remapCoordinateSystem` → `getOrientation`, whose `orientation[0]` is radians in -π..π and needs 0-360 normalisation), contrasting it in a table with the accelerometer + magnetometer pairing it replaces and with `TYPE_GAME_ROTATION_VECTOR`, which drops the magnetometer and therefore has no north reference at all. A device measurement (SM-A725F / Android 13, qualcomm "Rotation Vector Non-wakeup") settled one implementation detail rather than leaving it to a defensive guess: `event.values` arrives with **5** elements, not the 3-4 the rotation vector is defined as, but passing that full array to `getRotationMatrixFromVector` raises nothing and yields a rotation matrix identical to one built from a `copyOf(4)` copy, so the truncation was removed rather than allocating a new array on every event. The display-rotation card reads the live `Surface.ROTATION_*` value through `ContextCompat.getDisplayOrDefault(context).rotation` — chosen over the deprecated `WindowManager.defaultDisplay` so the file stays warning-free on minSdk 24 — keyed on `LocalConfiguration` so rotating the device recomputes the axis mapping on screen. The centrepiece is a deterministic wrap-around demo that needs no sensor and therefore runs on an emulator: feeding the eight-step sequence 348° → 15° through the textbook `previous + α × (raw − previous)` low-pass ends at 118.7° — the opposite side of the dial — because the subtraction crosses 359°/0° and produces −356, while normalising the delta to -180..180 first (`((raw - previous + 540) % 360) - 180`) tracks it to 4.8°; both series are computed live and shown step by step next to two needles. The live compass draws the raw azimuth as a grey needle outside the rotated rose and the filtered one as the red north needle inside it, and both are read via `State.value` inside the `Canvas` draw lambda so each sensor event triggers a redraw rather than a recomposition of the surrounding card. `SENSOR_DELAY_UI` registration is scoped to `DisposableEffect` with `unregisterListener` in `onDispose`, and the pitfall card covers magnetic-interference and `onAccuracyChanged` calibration states plus the magnetic-vs-true-north correction via `GeomagneticField.getDeclination()`
  - Android 16 Live Updates Notification — the project's first notification example of its own (`NotificationCompat` appeared only once before, in `LocationTrackingService`'s foreground notification). `NotificationCompat.ProgressStyle` replaces the single-colour bar of `setProgress(max, progress, indeterminate)` with coloured segments, positioned point markers, and tracker/start/end icons, and the example drives all of it from one delivery scenario (20 + 40 + 15 + 45). Two API contracts are settled by reading core 1.17.0 bytecode rather than release notes, then confirmed by measurement on a device. (a) There is no `setProgressMax` — `getProgressMax()` sums the segment lengths on the spot, skips lengths of zero or less, catches the `Math.addExact` overflow and falls back to 100, and returns 100 only when the segment list is empty; measured on SM-A725F/API 33, an empty style is 100, the delivery scenario is 120, and `Segment(0) + Segment(30)` is 30, not 100. (b) `ProgressStyle.apply()` branches on `SDK_INT >= 36`: above it every segment, point, icon and `styledByProgress` flag is transferred to a platform `Notification.ProgressStyle`, below it the whole style collapses into `setProgress(getProgressMax(), min(progress, max), indeterminate)` — a plain bar with the segments and points dropped. The values themselves survive either way, because `NotificationCompatBuilder.build()` calls `Style.addCompatExtras(extras)`, so a card dumps the built `Notification`'s extras live on whatever device is running — no posting and no `POST_NOTIFICATIONS` permission needed to see `android.progressSegments` (4 bundles), `android.progressPoints` (2), `android.requestPromotedOngoing`, `android.shortCriticalText` and the `COMPAT_TEMPLATE` marker. That dump also exposed an ordering detail worth its own warning: the fallback writes `min(progress, max)` into `android.progress` first and `addCompatExtras` then overwrites it with the raw value, so building with progress=999 against max=120 leaves **999** in extras while the bar renders 120 — the extras are the request, not the render. Promotion itself is never the app's decision: `setRequestPromotedOngoing(true)` carries no version branch at all and merely puts a boolean in extras, and `canPostPromotedNotifications()` returns false without consulting the platform whenever `SDK_INT < 36`, so a false reading must not be read as "the user disabled promotion". The demo posts and updates a real notification (auto-advance throttled to 0.8s, since notifying on every progress change is throttled by the system) and states plainly that segment/point rendering can only be seen on an Android 16 device — the available device is Android 13, where only the collapse path is verifiable

  - Picture-in-Picture compat — the project's first PiP code of any kind (`PictureInPicture` appeared zero times, and no activity declared `supportsPictureInPicture`). Uses `PictureInPictureParamsCompat` from androidx.core **1.18.0**, whose value is that its Builder accepts all nine fields with no API gating at all, moving every version branch into one place: `toPictureInPictureParams()` (`@RequiresApi(26)`). Reading that method's bytecode shows it comparing `SDK_INT` against 33 then 31 and dispatching to `Api33Impl.create` (all nine), `Api31Impl.create` (five — expandedAspectRatio, closeAction, title and subTitle silently dropped) or `Api26Impl.create` (three — seamlessResize and autoEnter dropped too), so a field set on an older device disappears without any exception. A readback card makes that visible rather than asserted: it converts the live options and reads the platform object back through `getAspectRatio`/`getTitle`/`isAutoEnterEnabled` and the rest — all nine getters carry `since="33"` in the SDK's own `api-versions.xml` even though the class itself is API 26, so the card is gated at 33 and states that below it the values cannot be inspected at all rather than pretending they were lost. Device measurements (SM-A725F / API 33) settle three things the docs do not: (a) the platform `toString()` reports `hasSetActions=true` even when actions were never set, because the compat layer always passes a list, while `getActions()` honestly returns zero; (b) the aspect-ratio guard rejects with "Aspect ratio is too extreme (must be between 0.418410 and 2.390000)" and 239:100 passes while 240:100 fails — but so does 4184:10000, because the printed lower bound is a rounded 1/2.39 = 0.41841004… and 0.4184 falls just under it, a trap the message itself invites; (c) `enterPictureInPictureMode` throws `IllegalStateException("Activity must be resumed to enter picture-in-picture")` from a non-resumed activity while `setPictureInPictureParams` succeeds in that same state, which is what makes it possible to pre-seed autoEnter parameters before the screen is visible. PiP mode itself is observed without touching the activity class, via `ComponentActivity.addOnPictureInPictureModeChangedListener`, and the screen swaps to a minimal composable while in PiP. Adds `android:supportsPictureInPicture` and the four `configChanges` flags to `BlogExampleActivity`. One thing stayed unverified and is labelled as such on screen: entering the PiP window itself — the connected device was keyguard-locked so no test harness could resume the activity, and the API 34 emulator started as a substitute failed to keep the app APK installed

  - WorkManager Test Harness — the project had a WorkManager example and three instrumented-test examples, but the intersection was empty: `WorkManagerTestInitHelper`, `TestDriver`, `SynchronousExecutor` and `TestListenableWorkerBuilder` all appeared zero times. Adds `androidx.work:work-testing` at the runtime work version already in use (2.9.1 — its aar-metadata asks only for `minCompileSdk=34`/`minAGP=1.0.0`, so no upgrade was needed) and ships five instrumented tests that actually pass on a device, with the screen documenting what they measured. The centrepiece is that scheduling conditions are satisfied *without* creating them: a request constrained on `NetworkType.CONNECTED` plus `setRequiresCharging(true)` sits at `ENQUEUED` after `enqueue`, and `testDriver.setAllConstraintsMet(id)` alone moves it to `SUCCEEDED` with output `echo = "HELLO"` — the phone was neither charging nor manipulated. The same holds for time: a 24-hour `setInitialDelay` stays `ENQUEUED` until `setInitialDelayMet`, after which it is `SUCCEEDED`, which is how a 15-minute periodic minimum stops being a reason not to test. The second half drops WorkManager entirely — `TestListenableWorkerBuilder<W>` runs one worker in isolation, and injecting `setRunAttemptCount` exercises retry branches without ever failing for real: measured `Retry` at 0 attempts against `Success {mOutputData=Data {attempt : 2, }}` at 2, alongside `Success {mOutputData=Data {echo : ISOLATED, }}` and `Failure {mOutputData=Data {}}` for the missing-input branch. Boilerplate is folded into a reusable `WorkManagerTestRule` that owns initialization, the `TestDriver` handle (only valid after initialization) and `cancelAllWork()` cleanup, since WorkManager is a process singleton and state leaks between tests. The example screen deliberately does not run any of this itself: `initializeTestWorkManager` swaps the process-wide WorkManager singleton for a test implementation, which would hijack the instance the existing WorkManager example uses — so the executable code lives in `androidTest` and the screen carries the explanation plus the measurements, matching how the neighbouring Paparazzi/Roborazzi example is structured. Also documents the three `ExecutorsMode` overloads and that `enqueue(...).result.get()` / `getWorkInfoById(id).get()` are blocking `ListenableFuture` waits

  - Form State & Validation — the axis above the project's eight existing `ui/text/` examples, which are all about a single field (max length, syntax highlighting, rich content, auto-sizing). At the time of writing the project used `ImeAction`/`KeyboardActions` zero times, had never passed `isError` to a text field, and had no `supportingText` anywhere, so multi-field forms were entirely uncovered. Three fields carry the identical email rule and differ only in *when* it runs — on every keystroke, on focus loss, or on submit — and each counts how many times its error state flipped, so the cost of eager validation is a number on screen rather than an opinion. The four-field form (name / email / password / confirm) wires `KeyboardOptions(imeAction = ImeAction.Next)` to actual focus movement through `FocusRequester` in `onKeyboardAction`, since the IME option alone only changes the key's shape, and it keeps `supportingText` filled at all times — with the help text when there is no error — because a slot that appears only on error grows the field and pushes everything below it, which a dedicated card demonstrates by measuring the container height live through `onGloballyPositioned`. Password confirmation is the case that forces the whole design: it cannot be judged from its own value, so validation belongs to the form rather than the field. A separate card puts a plainly-computed enabled flag next to a `derivedStateOf` one and lets each button count its own recompositions. All rules are plain functions outside composition so they stay unit-testable, and `TextFieldState` changes are observed with `snapshotFlow` since that API has no `onValueChange`. Reimplements the technique from a KMP+KSP form library (AW #743) with nothing but Compose and material3, the same way the auto-skeleton example handled a Compose-Multiplatform-only library. Device measurement did not happen this cycle and the guide says so: the connected phone sat behind a keyguard with a system-update dialog on top, and the API 34 emulator brought up as a substitute did not keep the app APK installed during instrumentation — the screen computes every number itself at runtime instead

  - Coroutine Stack Trace Recovery — the project had fourteen `suspendCoroutine` sites and a whole `concurrency/` package, but nothing about what happens to a stack trace when it crosses a suspend boundary: `CopyableThrowable` and `DEBUG_PROPERTY` both appeared zero times. Nothing was added to the dependency list — everything needed already ships in the resolved `kotlinx-coroutines-core` 1.10.1. The screen throws the same exception down `loadProfile → fetchRemote (withContext IO) → parsePayload (withContext Default)` in three variants that differ only in their fields, and counts what came back: whether the caught instance is the original or a copy, whether a `cause` is attached, how many `_COROUTINE` frames the trace holds, and whether the caller is in it at all. Three facts are read out of the library's bytecode rather than its docs. (a) The switch is `DEBUG`, which for a null or `"auto"` value of `kotlinx.coroutines.debug` is simply `desiredAssertionStatus()`, with `RECOVER_STACK_TRACES = DEBUG && systemProp("kotlinx.coroutines.stacktrace.recovery", true)` on top — so recovery is **off by default on Android**, where the runtime does not enable assertions, and a debug build does not change that. Measured on SM-A725F / Android 13: assertions false, zero artificial frames, `cause` null, and the raw trace ending in `BaseContinuationImpl.resumeWith` → `DispatchedTask.run` → `CoroutineScheduler.runSafely` with the caller nowhere in it. (b) Both values are `val`s computed once at class load, so calling `System.setProperty` from a screen is already too late — the card proves it by setting the property, re-running, and showing the artificial-frame count unchanged (measured 0 → 0), then restores the previous value so no global state leaks into other examples. (c) Reflective copying is skipped entirely for any exception that declares even one field of its own: `createConstructor` opens with `if (throwableFields != fieldsCountOrDefault(clazz, 0)) return nullResult`, which is why a plain exception recovers while the same exception plus a `requestId` does not, regardless of its constructor shape — and why `CopyableThrowable.createCopy()` exists at all. That contrast was confirmed in a JVM unit test, where Gradle enables assertions and recovery therefore runs: the field-less exception came back copied with the original as `cause` and an `at _COROUTINE._BOUNDARY._(CoroutineDebugging.kt:42)` frame in the middle, the one-field exception came back raw and uncopied, and the `CopyableThrowable` one came back copied with `req-42` intact. A fourth card reproduces recovery with public API only on a device where it is switched off — `createCopy()`, then `setStackTrace` of the exception's own frames plus a boundary element built to the library's rule (class `_COROUTINE._BOUNDARY`, method `_`) plus a caller stack captured before entering the suspend call — measured on device from a Main-dispatched coroutine as caller-absent in the exception, caller-present in the entry capture, caller-present in the merged result. The pitfalls close the loop: what catch receives is not the instance that was thrown, `_COROUTINE` frames are markers rather than executed code and will confuse a trace parser, and the copying is not free, which is why this is a debugging switch and not a production setting

  - NavigationEvent Dispatcher — the first use of `androidx.navigationevent` in the project (the name collided only with a hand-rolled sealed class of the same name). Adds `navigationevent:1.1.2` and `navigationevent-compose:1.1.2`, both stable, whose aar-metadata asks for `minCompileSdk=36`/`minAGP=8.9.1` against the project's compileSdk 36 and AGP 8.13.2. The existing predictive-back example is about one direction and one number — the platform gesture's progress; this one is the layer above it, where **back and forward** are symmetric, the handler carries **currentInfo / backInfo / forwardInfo**, and progress lives in a **transitionState** rather than in a callback. The demo needs no swiping at all: `DirectNavigationEventInput` exposes `backStarted` / `backProgressed` / `backCompleted` / `backCancelled` (and the forward four), so the whole gesture is reproducible from buttons, which is also what makes it testable. Everything the screen claims was measured against the core API on a device (SM-A725F / Android 13) rather than read from docs. The state machine runs `Idle` → `InProgress(direction = -1)` → `Idle` on completion and returns to `Idle` on cancellation. Gating is silent: with `isBackEnabled = false`, injecting a start and a completion produces **zero** callbacks and no exception, because no handler accepts the event and the dispatcher's fallback was never supplied. Two details contradict what the API's shape suggests. First, **the sequence is not enforced** — calling `backCompleted()` with no preceding `backStarted()` still fires the callback, while a lone `backProgressed()` is dropped, so ordering is the input source's responsibility and the screen's disabled buttons are a UI choice rather than an API constraint. Second, `TRANSITIONING_BACK` is **-1**, not 0 — 0 is `TRANSITIONING_UNKNOWN` — and `NavigationEvent()` defaults its `swipeEdge` to `EDGE_NONE` (2). Ordering of the info lists is not a matter of taste either: `NavigationEventHistory.mergedHistory` concatenates backInfo, then currentInfo, then forwardInfo, verified as `[홈, 목록, 상세, 설정]` with `currentIndex = 2`, so backInfo must be oldest-first. The composable handler resolves its dispatcher through `LocalNavigationEventDispatcherOwner` and throws if it is empty, and `rememberNavigationEventDispatcherOwner` defaults its `parent` to that same local — so a root screen has to pass `parent = null` explicitly, with both failure messages quoted on screen. One dependency-graph side effect is documented rather than hidden: navigationevent-compose's pom requires compose ui/runtime 1.11.2, which outranks the BOM's 1.11.1 and pulls **those two artifacts only** to 1.11.2 while foundation, animation and material stay at 1.11.1; the API the library actually uses (`androidx.compose.runtime.HostDefaultKey`) already exists in 1.11.1, so the bump is a compatibility requirement rather than a functional one

  - Text Selection Control — the project's eight existing `ui/text/` examples are all about input; this one is the read side, where the user drags across text the app merely displayed. `SelectionContainer` opens selection for everything inside it and `DisableSelection` carves exceptions out of the same container, both shown as things to actually drag rather than described. The example exists mostly because two assumptions that sound obvious turned out to be wrong, and both were settled by measurement. First, **the selection content cannot be read from app code in this version**: foundation 1.11.1 does ship a `SelectionContainer(modifier, selection, onSelectionChange, children)` overload and a `Selection` class, and `javap` shows both as public — but they are Kotlin `internal`, which compiles to JVM public, so the build fails with `Cannot access 'data class Selection : Any': it is internal in file.` The card quotes that error verbatim, because the general lesson (bytecode visibility is not Kotlin visibility) is worth more than the specific API. Second, and more surprising: **replacing `LocalTextToolbar` no longer intercepts the selection menu by default.** Compose 1.11's foundation moved the selection context menu to `androidx.compose.foundation.text.contextmenu`, gated on `ComposeFoundationFlags.isNewContextMenuEnabled`, whose static initialiser sets it to **true**. Instrumented on a device (SM-A725F / Android 13) with a recording `TextToolbar` and a `longClick` to select: at the default the toolbar received **zero** `showMenu` calls and stayed `Hidden`; flipping the flag to false at runtime and rebuilding the subtree with `key()` produced **two** calls with status `Shown`. The same run settled what arrives in those calls — `copy` and `selectAll` only, since a read-only selection has nothing to cut or paste, so a custom toolbar can only draw what it is handed. The screen carries that toggle so the difference is reproducible by hand, and restores the flag in a `DisposableEffect` because it is process-global state. The two findings combine into the one workaround that does work today: because the custom toolbar owns the `onCopyRequested` callback, invoking it and then reading `LocalClipboard.getClipEntry()?.clipData` yields the selected string — with the caveat, noted as a pitfall, that Android 12+ shows the user a toast whenever an app reads the clipboard. A closing card contrasts this against Compose 1.12.1's `SelectionState` (`rememberSelectionState()`, `selectedTexts`, `selectableTexts`, `selectAll()`, `clear()`, `extendSelectionByWord()`, plus a built-in `Saver`), which turns "read the selection" into public API — and notes that foundation 1.12.1's aar-metadata asks for `minCompileSdk=37`, so this project cannot adopt it yet

  - Dialog Background Blur — the project had no blur coverage of any kind at the window level (`setBackgroundBlurRadius`, `FLAG_BLUR_BEHIND` and `Modifier.blur` all appeared zero times; the seventeen `RenderEffect` hits are the AGSL and motion-blur examples). The example starts from the confusion the word itself causes: "blur" names three different things, and they differ in *what* gets blurred — `Modifier.blur` affects only what that composable drew, `Window.setBackgroundBlurRadius` affects the window's own background area, and `LayoutParams.blurBehindRadius` together with `FLAG_BLUR_BEHIND` is the only one that reaches **other windows behind yours**, which is what "blur the screen behind my dialog" actually means. All three require API 31, which matters in a project with minSdk 24. Compose's `Dialog` window is reached through `(LocalView.current.parent as? DialogWindowProvider)?.window`, and sliders drive the two radii and the dim amount side by side so the difference between "behind the window" and "inside the window" is visible rather than described. The device measurement is the centrepiece and it landed on exactly the trap the screen warns about: on SM-A725F / Android 13 (API 33) the instrumented probe set `blurBehindRadius = 40` and `dimAmount = 0.4`, added both `FLAG_BLUR_BEHIND` and `FLAG_DIM_BEHIND`, and read every one of them back successfully from `window.attributes` — while `WindowManager.isCrossWindowBlurEnabled()` reported **false**. The API call succeeds, the values stick, and nothing appears on screen, which is why support has to be checked in two layers and why the screen subscribes to `addCrossWindowBlurEnabledListener` rather than reading the flag once. The fallback card builds what apps needed before API 31: record the background into a `GraphicsLayer`, pull it out with `toImageBitmap()`, then downscale and run two box-blur passes, timing each step so it is clear that the downscale factor — not the radius — dominates the cost. That card also carries a second measured failure: capturing a layer that has never been drawn throws `IllegalArgumentException("width & height must be > 0")`, reproduced in instrumentation where the device sat behind a secure keyguard so no draw pass ran and `layer.size` stayed `0x0`. The screen now checks the size first and explains the situation instead of crashing. The pitfalls close on what the fallback fundamentally cannot do: it is a still image, so a moving background stops moving, and another app's window was never capturable in the first place

  - IME Interactive Control — the existing `ImeStateUtil.rememberImeState()` only exposes a single boolean (`WindowInsets.isImeVisible`); this example covers the two axes it does not touch. `Modifier.imeNestedScroll()` hands the leftover scroll delta at a list's scroll bounds to the keyboard's own show/hide animation, so a drag gesture can pull the IME open or closed interactively (API 30+ only — the modifier is a documented no-op below `Build.VERSION_CODES.R`, and the example surfaces that with a live `Build.VERSION.SDK_INT` check rather than a static note). `WindowInsets.Companion.imeAnimationSource`/`imeAnimationTarget` expose the before/after inset values of an in-flight IME animation, and since `WindowInsets.Companion.ime` is the interpolated current value, `(current - source) / (target - source)` reproduces the system keyboard animation's real progress on every frame; a custom badge is offset by that same progress to demonstrate syncing arbitrary UI to it instead of guessing at a matching `animateFloatAsState` curve
  - Indirect Pointer Input Pipeline — contrasts two separate mechanisms Compose exposes for trackpad-like input. `IndirectPointerInputModifierNode` (new, `DelegatableNode`-based, no higher-level `pointerInput{}`-style helper exists yet so it is delegated via a hand-written `Modifier.Node` + `ModifierNodeElement`) delivers a trackpad cursor's raw position/pressed-state/directional-axis hint directly, independent of multi-touch semantics. Separately, the existing `PointerEventType` already carries stable `PanStart`/`PanMove`/`PanEnd`/`ScaleStart`/`ScaleChange`/`ScaleEnd` values that `MotionEventAdapter` synthesizes — confirmed by bytecode, not documentation — only when `MotionEvent.getClassification()` reports `CLASSIFICATION_TWO_FINGER_SWIPE`(API 29+)/`CLASSIFICATION_PINCH`(API 34+), gated by `ComposeUiFlags.isTrackpadGestureHandlingEnabled` (`true` by default), so existing multi-touch-aware widgets (`Modifier.transformable`/`scrollable`) get trackpad support "for free". A single live capture box lets a two-finger touchscreen pinch prove the negative directly on any device: the Pan*/Scale* chips never light up, only individual `Touch`-typed Press/Move/Release changes do. Also pins an opt-in boundary split found only by probe-compiling a throwaway instrumented test: the production interface (`IndirectPointerInputModifierNode`, `IndirectPointerEvent`, etc.) needs no `@OptIn`, while the test-only injection hooks (`RootForTest.sendIndirectPointerEvent`, the `IndirectPointerEvent(MotionEvent)` factory) require `@OptIn(ExperimentalIndirectPointerApi::class)` — a marker declared in a different subpackage than the API it gates. Runtime dispatch of a synthesized indirect event was left unverified this cycle: the only connected device already had the app installed under a separate Secure Folder user profile with a mismatched signature, blocking a debug reinstall, and reaching into that profile was declined
  - `kotlin.time` Stdlib API — the project's first use of the `kotlin.time` clock/duration family; every prior timing measurement in the codebase used `System.currentTimeMillis()` or the JVM-only `kotlin.system.measureTimeMillis`. Separates "what time is it" from "how long did that take": `Clock.System.now()` returns an `Instant` wall clock that can jump on NTP sync or timezone changes, while `TimeSource.Monotonic.markNow()`/`elapsedNow()` is immune to those jumps and is the correct tool for elapsed-time measurement. `measureTimedValue { }` returns both the computed value and a `Duration` in one call, and a live side-by-side card runs the identical `sumOfSquares` computation through both `System.currentTimeMillis()` subtraction and `measureTimedValue`, so whichever one rounds to `0ms` on the current device is shown directly rather than asserted. `TestTimeSource` demonstrates advancing elapsed time deterministically (`+= 1.seconds`) with no real `delay()`, for testing timeout/retry logic without waiting. Corrects the opt-in assumption made at candidate registration (2026-08-10): `javap` on `kotlin-stdlib-2.4.0.jar` shows `Clock`/`Instant`/`TestTimeSource` all carrying `@SinceKotlin("2.3")` + `WasExperimental(markerClass=[ExperimentalTime])`, which looked like an opt-in requirement, but actually compiling with `@OptIn(ExperimentalTime::class)` removed built successfully — `WasExperimental` is compiler-facing history metadata for an API that already graduated to stable, not a live `@RequiresOptIn` gate. None of the four APIs used here need `@OptIn` in this project's Kotlin 2.4.0
  - Sealed Interface Domain Error Handling — Kotlin has no checked exceptions, so a `throw`-based function's signature gives no indication of what can go wrong; this example contrasts that with returning a sealed interface (`OrderOutcome` = `Success` or `Failure(OrderError)`) directly from the function. A throwing card (`placeOrderThrowing`, failure modes documented only in `@throws` KDoc) sits next to a sealed-return card (`placeOrderSealed`) with four scenario buttons (valid order / zero quantity / stock exceeded / outside service hours) whose outcome is rendered through a nested exhaustive `when` — no `else` branch, because every `OrderOutcome` and `OrderError` subtype is listed. A dedicated card explains the exhaustiveness contract in prose: adding a new `OrderError` subtype turns every `when` over it into a compile error until the new branch is handled, catching missed cases at write-time rather than at runtime. Implemented with plain Kotlin stdlib (`sealed interface` + `data class`) — no Arrow `Either` dependency needed. Distinct from the existing `SealedClassInterfaceExample`, which teaches the sealed-class language feature itself via a file-local UI-state type (`ApiResult<T>`); this example's axis is sealed interfaces as a domain function's *return type*, an architecture pattern the project's `domain/` layer (e.g. `GetArticleUseCase`) does not otherwise demonstrate
  - Coordinate-Based Spotlight Overlay (coachmark) — a mini mock screen holds three icon targets, each reporting its `boundsInWindow()` through `Modifier.onGloballyPositioned`; pressing "코치마크 시작" launches a `Popup` sized and positioned (via a hand-written `PopupPositionProvider` that ignores the anchor and returns a fixed window offset) to exactly overlay that mock screen, independent of the surrounding `Card`/`LazyColumn`'s own clipping — the reason a plain overlapping `Box` was rejected as the mechanism, since the scrim would be clipped to its parent's bounds. The "hole" itself is built by `Path().apply { op(fullScreenPath, holePath, PathOperation.Difference) }` (full-canvas rect minus a rounded-rect around the current target) and painted through `clipPath`, so the target area shows the untouched mock screen underneath a `Color.Black.copy(alpha = 0.75f)` scrim everywhere else. Stepping to the next target animates the hole's four edges independently via `animateFloatAsState`, read directly inside the `Canvas` draw lambda (`State.value`, not a `by` delegate in the composable body) so each frame only triggers a redraw, not a recomposition of the surrounding tooltip/buttons. Scoped intentionally to the mock screen rather than the real device screen to sidestep status-bar/edge-to-edge inset math, documented as an explicit out-of-scope decision in `exampleGuide.kt`
  - Auto Skeleton Loading Detection Modifier — contrasts the project's existing manual-branch Shimmer examples (`ShimmerExampleUI`/`TextShimmerExampleUI`, where each call site receives an `isLoading`-equivalent value and builds a parallel skeleton-shaped `Spacer` tree by hand) with a `CompositionLocal`-propagated automatic pattern: `SkeletonContainer` owns a single loading flag and one shared `rememberInfiniteTransition` shimmer phase, and `Modifier.autoSkeleton()` reads both from `LocalSkeletonScope.current` with no per-element parameter. The shimmer overlay reuses the element's own already-measured `DrawScope.size` instead of a hand-matched parallel tree, made visible in the demo card where two profile-row texts of different lengths ("김코틀린" vs "Compose 개발자") each get a shimmer bar auto-sized to their own width. Crossfade independence comes from modifier ordering: `drawWithContent` (outer) draws the real content — wrapped by the inner `graphicsLayer { alpha = contentAlpha.value }` — then draws the shimmer rectangle directly, outside that alpha, so content and shimmer fade on separate curves; reversing the two would fade the shimmer along with the content. Reimplements only the technique from a Compose **Multiplatform**-only library article (AW #741) using this project's standard Jetpack Compose APIs (`composed{}`, `drawWithContent`, `graphicsLayer`) rather than adopting the KMP-only library itself
  - Deterministic Images in Screenshot Tests — the flakiness axis the project's two existing screenshot examples do not cover (`ScreenshotTestingExampleUI` explains Paparazzi/Roborazzi mechanics, `PreviewDrivenScreenshotExampleUI` derives the preview matrix; neither addresses why a golden diff appears without a code change).
