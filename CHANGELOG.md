## 2026.10
- New examples added
  - Ktor SSE client added to the Server-Sent Events example (Ktor 3.6.0, #105). No dependency changed - Ktor 3.6.0 and okhttp-eventsource 5.0.0 were already in place. The screen now receives the same Wikimedia stream either through okhttp-eventsource callbacks or through `client.sse(url) { incoming.take(10).collect { } }` on Ktor's OkHttp engine (MockEngine has no SSE support), and records for each run the first event's fields, thread counts before / while receiving / one second after stopping, how it ended and how many events arrived after the stop decision. Measured on a Galaxy A72: okhttp-eventsource runs two threads of its own (`okhttp-eventsource-events` / `-stream`), gone a second after `close()`, while Ktor only uses OkHttp's threads; Ktor stops by leaving the block or cancelling the job, with no event processed afterwards, whereas the callback side keeps delivering events until `close()` has gone through (0 to 15 per run). The existing code only dropped them once its reference had been cleared, which let an 11th character in after deciding to stop at 10; it now drops them from the moment the stop is decided. Leaving the screen stops both within 1.5 s - Ktor through the `viewModelScope` cancellation plus `client.close()` in `onCleared`, okhttp-eventsource through the `close()` already in `onCleared`. Ktor's `SSEConfig` defaults to `reconnectionTime = 3s` and `maxReconnectionAttempts = 0`, i.e. no reconnection unless enabled, unlike okhttp-eventsource's retry strategy.
  - Power-Assert (Kotlin compiler plugin 2.4.20, #102). The plugin ships with Kotlin, so its version follows `kotlinVersion`; applying it also adds `kotlin-power-assert-runtime` (27 KB, depends only on the stdlib) to every compilation it touches. Two things in 2.4.20 differ from older write-ups, both read from the Gradle plugin bytecode and confirmed in the build: the default `compilationFilter` (TESTS) selects only a compilation named exactly `test`, while AGP 9's built-in Kotlin compilations are `debug`, `release`, `debugUnitTest` and `debugAndroidTest`, so on Android the default applies to nothing and the filter has to list the names; and `includedSourceSets` is deprecated in favour of that filter. The screen feeds the same condition to a plain function and to a `@PowerAssert` function (new in 2.4.20, experimental): the plain one only knows "condition is false", the power one shows every sub-expression (13600 vs 13000, a count of 2, a null chain, `'m'`, the range). Inside the function `PowerAssert.explanation` returns a `CallExplanation` - argument ranges and typed sub-expressions such as `EqualityExpression(lhs, rhs)` - from which the example builds its own message. Measured on a Galaxy A72 in debug and release: a side-effecting sub-expression is evaluated once; the explanation is passed as a lambda to a generated `powerCheck$powerassert` overload, so the success path calls no `toString` at all; a reflective call gets a null explanation. `kotlin.assert` only checks when `kotlin._Assertions.ENABLED` is set: on the device the debug build throws and the release build skips it, although `desiredAssertionStatus()` is false in both. Applied unchanged to `kotlin.test` unit tests, `expected:<13000> but was:<13600>` gains the expression diagram (`PowerAssertExampleTest` checks it), and the instrumented tests' `assert` calls get diagrams too. Found while verifying: with the debug-only HotSwan hot reload, a `@PowerAssert` function body throws `NotImplementedError` because the intrinsic is not replaced in the code HotSwan runs, and a transformed call site evaluates a side-effecting expression three times; excluding `PowerAssertChecksKt` and `PowerAssertViewModel` through `hotSwanCompiler { exclude(...) }` fixes both (documented in `ComposeHotReloadGuide.md`).
  - Multi-process app structure (`android:process` / `isolatedProcess`, #114). No dependency changed. The same Messenger service is declared three times as empty subclasses - default process, `:remote`, and `:isolated` with `isolatedProcess="true"` - and each process reports its own PID, UID, process name, singleton counter, Koin state and PSS. `Application.onCreate` runs in every process: with the guard temporarily removed, Koin started in all three processes; `BaseApplication` now starts Koin only when `getProcessName()` (API 28+, `/proc/self/cmdline` below that - truncated at 98 characters on the test device, which does not affect the main-process check) equals `applicationInfo.processName`, giving true/false/false. Binder limits, measured on a Galaxy A72 (Android 13): a same-process service receives the `Message` object itself, so even 2 MB passes, while `:remote` fails from 600 KB with `TransactionTooLargeException`. Raw `transact` accepts at most 1,040,384 bytes synchronously (1 MB minus two pages) and 520,096 bytes oneway; the Messenger boundary found by binary search (payload 519,922 ok / 519,926 fails) adds up to exactly 520,096 bytes once the 64-byte interface header and the 8-byte binder offset of `replyTo` are included. `Process.killProcess` on the remote PID (allowed for the same UID) is followed by `onServiceDisconnected`, then `binderDied`, then an automatic reconnect to a new process 2-6 s later, three times in a row; a first crash reconnects silently, but a second crash within a minute brings up the system error dialog (on Galaxy, "delete cache files?") and `onBindingDied`, with no reconnect until the client unbinds and binds again. A `Messenger` kept from before the death throws `DeadObjectException` even after the reconnect. The isolated process gets a fresh PID and UID on every bind (99016, 99017, 99018), a process name with the service class appended, INTERNET denied, `socket failed: EACCES` (the other processes reach `ECONNREFUSED`), ENOENT rather than EACCES for the file the main process wrote, and a `SecurityException` from `getRunningAppProcesses()`, where it is also absent when the main process asks. A bound `:remote` takes the client's importance (FOREGROUND 100) and stays cached after the screen unbinds, so the counter survives re-entry; the isolated process disappears at once. Release PSS: `:remote` about 104 MB right after install (76 MB of privately decompressed dex), about 20 MB after `speed-profile` dexopt, while `:isolated` stays near 100 MB even after dexopt.

## 2026.09
- New examples added
  - Ktor HTTP cache (HttpCache, Ktor 3.6.0, #113). Ktor 3.6.0 arrived with the SDK 37 bundle, so no dependency version changed; `kotlinx-io-core` 0.9.1, already resolved through Ktor, is now declared explicitly because the example calls `Path`/`SystemFileSystem` itself (the four resolved classpaths are identical before and after). A MockEngine origin answers `If-None-Match`/`If-Modified-Since` with 304 and records every request, so each call shows side by side whether it reached the server, which conditional header it carried, what the server returned, what the app received and whether `HttpResponseFromCache` fired. Measured: `max-age` is served without the server until it expires, then revalidated with `If-None-Match`; `no-cache` and ETag-only responses revalidate every time; `no-store` is never stored; without an ETag, `Last-Modified` drives `If-Modified-Since`; a changed ETag replaces the entry. A 304 is invisible to the caller - the app gets a 200 with the cached body, and the cache event fires for fresh hits and for 304s alike. `private` responses land in the private storage of a non-shared cache and are not stored at all when `isShared = true`. New in 3.6.0 (checked against the 3.5.2 jar): `clearAllCaches()` empties both storages (and deletes the files of a `FileStorage`), `FileStorage(Path, FileSystem)` is kotlinx-io based, and the old `FileStorage(File)` now delegates to it - both return a `CachingCacheStorage`. A new client pointed at the same directory hits the disk cache on its first request, while an in-memory storage misses. `acceptHeaderMergeStrategy`: with `accept(text/plain)`, `Default` sends both `text/plain` and `application/json`, `SkipIfPresent` only `text/plain`.
  - Mesh Gradient (Compose 1.12, #107). No dependency changed - Compose 1.12.1 arrived with the SDK 37 bundle. The only public entry point is `MeshGradientPainter(rows, columns, hasBicubicColor) { setVertex(...) }`: `MeshGradientConfig` and `MeshGradientRenderer` look public in the bytecode but are Kotlin `internal`, so using them fails to compile. rows/columns count patches, positions are normalized, and the four control points are offsets relative to the vertex. The screen compares bilinear and bicubic colour interpolation side by side, lets you drag vertices and switch control points between inferred and explicit, and verifies the inference rule taken from the bytecode (0.33 x neighbour direction x distance) by rendering both versions - pixel difference 0 in three layouts. A red-to-blue 1x1 mesh reads #8C53A2 at the midpoint, equal to `lerp(Red, Blue, 0.5f)` (OkLab), while `Brush.horizontalGradient` reads #7F0080. Found while verifying: the 1.12.1 renderer calls `Canvas.drawVertices` with a default (black) `Paint`, and on the Galaxy A72 (Android 13, API 33) the platform multiplies vertex colours by the paint colour, so every mesh renders solid black - on screen, in a software bitmap and in a GraphicsLayer capture. Pixel emulators on API 30/34/35 ignore the paint colour and render correctly. The example detects this at startup and turns on a compatibility mode that renders through a software canvas whose `drawVertices` swaps in a white paint (release: ~7.2 ms -> ~25 ms per frame for a 3x3 mesh). The release notes mention `Canvas.drawMesh`, but the 1.12.1 aar contains no `drawMesh` call.
  - Composable-scoped LifecycleOwner (lifecycle 2.10, #104). lifecycle 2.10.0 was already resolved through Koin 4.2.2, so no dependency changed. `rememberLifecycleOwner(maxLifecycle, parent)` is the only public entry point - the owner class behind it, `ComposeLifecycleOwner`, is internal (checked with javap), and its state is min(parent, cap), with the cap applied through a `LaunchedEffect` and `ON_DESTROY` sent when the subtree leaves composition. The screen caps every HorizontalPager page except the settled one at STARTED and runs a ticker inside `repeatOnLifecycle(RESUMED)`. Measured on a device over 2 s at a 200 ms tick: capped on page 0 gave 10/0/0, uncapped gave 10/10/10 (the peeking and pre-composed neighbours are all RESUMED when they share the screen's owner), capped on page 1 gave 0/10/0, and a background round trip stopped every page and resumed only the current one. A playground changes the cap of a child owner and logs its events. The observer is deliberately not removed in `onDispose`, so that hiding the child still records ON_PAUSE -> ON_STOP -> ON_DESTROY. The probe also showed that scrolling that LazyColumn item out of view takes the same DESTROYED path and recreates the owner from ON_CREATE on return; the screen now says so.
  - WorkManager execution and schedule event listeners (work 2.12, `60bd145e`). WorkManager 2.12.0 reached stable, so the project bumped work-runtime/ktx/testing 2.11.2 -> 2.12.0 first and confirmed nothing moved: the aar wants compileSdk 35 and AGP 8.6.0 (both already met), every transitive it names is lower than what the project resolves, and the five existing WorkManager instrumented tests produced identical results before and after. The new `ExecutionEventListener` (onStarted/onStopped/onFinished/onException, all abstract) and `ScheduleEventListener` (onEnqueued/onUpdated/onUnblocked/onCancelled/onPrerequisiteFailed, all with defaults) are suspend and register only on `Configuration`, one per app - a screen cannot attach its own, so `BaseApplication` registers them and a global recorder collects what arrives, the same shape the exception-handler example already used. Because the listeners see every worker in the app, demo work carries a tag and everything else is discarded. Four scenarios show which callback answers which question, measured on a device: a normal A->B chain (enqueue, unblock, start, finish for each), a failing chain where the execution axis stays completely silent and only `onPrerequisiteFailed` explains why B never ran, a cancellation that yields `onStopped(stopReason=1 CANCELLED_BY_APP)`, and a thrown exception that arrives twice - the 2.11 `Consumer` handler first at 637ms, the 2.12 suspend `onException` after at 719ms. The 2.11 handlers are neither removed nor deprecated in 2.12 (checked with javap), so the two are layers rather than alternatives. One bug was found and fixed during device verification: keeping the timeline's zero point in a field made it shared mutable state between the main thread and WorkManager's executor threads, and the second scenario started at 4702ms instead of 0 even though its list had been cleared; deriving the zero point from the first entry in the list removes the shared field entirely
  - API request signing (HMAC-SHA256) with replay protection (`fbd722ce`). The project had no coverage of request signing at all - `Mac.getInstance`, `SecretKeySpec` and `Hmac` were zero hits, and the 24 `nonce` hits all belonged to the Play Integrity mock, which answers a different question (is the device genuine, not is this request untampered). There was also no example of an OkHttp interceptor anywhere, despite the app using one for connectivity checks. The screen signs a canonical string of method, path, timestamp, nonce and the body's SHA-256, then shows what each guard actually catches: a normal request passes, a body swapped after signing fails the signature check, a request signed ten windows in the past is refused although its signature is valid, and replaying a previously accepted request is refused because the server has seen that nonce. The last two are the point - a signature alone does not stop replay. No network is involved: a second interceptor plays the server and builds the `Response` itself instead of calling `chain.proceed()`, so the real interceptor pipeline runs with no server to host. Signature comparison is demonstrated by counting bytes read rather than timing, because a debug build runs through the interpreter and nanosecond measurements swing between runs (the Room benchmark hit exactly that, EX-BENCH-VARIANCE-01); the naive comparison reads 1, 9 and 32 bytes depending on where the forgery differs, while the constant-time one always reads all 32. Verified on a device (SM-A725F / Android 13)
  - Structured Concurrency Guardrails — kotlinx.coroutines 1.11.0 added compile-time guardrails for calls that break structured concurrency. The project already resolves 1.11.0 through Ktor 3.5.2, so no dependency changed, yet it had no coverage of `NonCancellable`, `runInterruptible`, `onSubscription` or `asDeferred`. Comparing the 1.11.0, 1.10.2 and 1.10.1 jars settled the scope: seven new WARNING overloads (`launch`/`async` taking a `Job` or `NonCancellable`, plus `runInterruptible(Job)`, `produce(Job)` and `future(Job)`), and the ERROR overloads for scope-less `launch`/`async`, which have existed since 1.10.2. Each warning overload simply delegates to the real builder, so the screen runs the flagged calls and measures what they break. When the parent is cancelled at 400 ms, the normal child stops at 418 ms. The `Job()`, `NonCancellable` and `Job() + Dispatchers.Default` children never appear in the parent's `children`, and they run to 1335 ms. `coroutineScope` returns an empty list after 15 ms because it has no children to wait for. `runInterruptible(Dispatchers.IO)` is released by interruption at 336 ms, while `runInterruptible(Job())` holds the thread until 1525 ms. The guardrail only checks the static type, so `launch(Job() + Dispatchers.IO)` and a `CoroutineContext` variable pass without a warning and behave the same way at runtime. Casting attempts show what the same release's three new APIs expose. `StateFlow.onSubscription` now returns a `StateFlow`, so `collectAsState()` needs no initial value. Its block also sees a `subscriptionCount` that already includes its own subscriber. `SharedFlow.asFlow()` hides both writes and `replayCache`; `asSharedFlow()` hides only writes. `CompletableDeferred.asDeferred()` blocks `complete()` through a cast but forwards `cancel()` to the original. `asFlow` and `asDeferred` are still `@ExperimentalCoroutinesApi`. Testing on a device also exposed a debug-only trap. The HotSwan 2.0 interpreter runs plain lambdas as a `Proxy`, so a checked `InterruptedException` escaping a `runInterruptible` block arrives wrapped in `UndeclaredThrowableException`. `runInterruptible` then cannot turn it into a cancellation, and the debug app crashes. Inline and suspend lambdas are unaffected (documented in `ComposeHotReloadGuide.md`).
  - Nav3 SceneStrategy Bottom Sheets — the project's first real `androidx.navigation3` usage (ui/runtime 1.1.7; the three older Nav3 examples remain simulations). A custom `SceneStrategy` turns entries tagged through metadata into an `OverlayScene` bottom sheet. Sheets stack because `NavDisplay` calls the strategy again with `overlaidEntries`. On a device, the screen under a sheet stays in composition: its ticker keeps counting, but its Lifecycle is capped at STARTED, and only the top overlay is RESUMED. A popped sheet stays on screen until `onRemove` returns, which took 244–277 ms for a 220 ms tween. Two library traps only showed up on the device. Sheets pushed one at a time are drawn in reverse order unless they are given a `zIndex`. And `NavDisplay`'s back handler works from the base scene, so a sheet without its own `NavigationBackHandler` lets a back press either leave the activity or pop several entries at once.
  - Custom Overscroll — the project had eighteen scroll/gesture examples and zero coverage of overscroll (`overscroll`, `OverscrollEffect` and `LocalOverscrollFactory` all appeared zero times), so the edge of a scroll container was the one part of the gesture pipeline never opened up. The screen contrasts four owners of the delta a list can no longer consume. (a) The platform default that `LocalOverscrollFactory` hands out — stretch on API 31+, glow below. (b) A hand-written `OverscrollEffect` that accumulates the leftover into an `Animatable` and renders it through a `DrawModifierNode` `translate`, so the content slides as one piece instead of stretching. (c) The same effect installed through `LocalOverscrollFactory` for a whole subtree, plus the `null` case — providing null is what removes overscroll entirely, and it is also why `rememberOverscrollEffect()` returns a nullable type. (d) `withoutVisualEffect()` / `withoutEventHandling()`, which split one effect in two so the list handles the events while a header above it does the moving — the way to lift an effect out of the container that would clip it. Reading the foundation 1.11.4 bytecode first settled three things the docs do not spell out: `OverscrollFactory` declares `equals`/`hashCode` as **abstract** members (a CompositionLocal value comparison, so a factory holding a lambda has to be remembered or it recreates the effect on every recomposition); `AndroidEdgeEffectOverscrollFactory` is not public, so "the default effect" can only be obtained through `rememberOverscrollEffect()`; and `LazyColumn` carries its own `overscrollEffect` parameter, which both renders the effect and feeds it events. Every mode runs through one probing decorator that wraps an arbitrary effect and records what `applyToScroll`/`applyToFling` actually receive, so the screen shows the delta, the part the list consumed, the part left over, and the fling velocity before and after — including the fact that nothing reaches the effect at all until the list stops consuming. Not yet verified on a device (none attached during this cycle); build, bytecode probes and the full-recompile warning scan are the evidence so far.
  - Worker Exception Handlers — WorkManager does not take the app down when a worker throws; it logs the throwable, closes the job as FAILED and moves on, so nothing reaches a crash reporter. work-runtime 2.11 opens that blind spot with two `Configuration.Builder` handlers, `setWorkerExecutionExceptionHandler` and `setWorkerInitializationExceptionHandler`, both taking a `Consumer<WorkerExceptionInfo>` (`workerClassName` + `workerParameters` + `throwable`) — the project had zero coverage of either. The screen enqueues four failures and contrasts what each one produces: a worker that throws inside `doWork()`, one that returns `Result.failure()`, one whose constructor throws, and one without a `(Context, WorkerParameters)` constructor. Reading the `WorkerWrapper` and `WorkerFactory` bytecode of 2.11.2 first settled where the calls sit — the initialization handler fires right after the "Could not create Worker" log and the execution handler after "failed because it threw an exception/error", and **both paths then return `Resolution.Failed`, so an escaped exception never becomes a retry**; the default factory walks `Class.forName` → `getDeclaredConstructor` → `newInstance` and rethrows each stage's throwable after logging it, which predicts different throwable shapes per stage. A device run (SM-A725F / Android 13) confirmed all of it and added two details worth the example's existence. (a) Four enqueued failures produce **three** reports: `Result.failure()` is an ordinary return path, so no handler is called, yet its `WorkInfo` state is `FAILED` exactly like the thrown case — the state alone cannot tell "failed" from "died". (b) The constructor case arrives as `InvocationTargetException` whose **`message` is null**, the real text living only in `cause` (`IllegalArgumentException`), while the missing-constructor case arrives as a bare `NoSuchMethodException` carrying the exact signature it searched for (`…MissingConstructorDemoWorker.<init> [class android.content.Context, class androidx.work.WorkerParameters]`) — collecting `throwable.message` alone would silently drop the only useful line for the wrapped case. The run also separated two attempt counters: the handler always sees `workerParameters.runAttemptCount` 0 (the pre-execution value), while the finished `WorkInfo` reports 1 for the two workers that actually ran and 0 for the two that were never constructed, and handlers were invoked on `WM.task-2`/`WM.task-3` rather than the main thread, which is why the screen routes everything through a `StateFlow`. Registration is the other half of the feature and it is app-global: `BaseApplication` now implements `Configuration.Provider`, and the manifest removes work-runtime's own `androidx.startup` `WorkManagerInitializer` with `tools:node="remove"` — without that removal the default initializer wins and the handlers are simply never called, with no error to explain why. The merged manifest was checked to confirm only that initializer is gone while HotSwan, emoji2, lifecycle, OkHttp and ProfileInstaller keep theirs, and every other Configuration value is left at its default so the existing WorkManager example behaves exactly as before
  - Display Cutout & Insets — the project had no insets example at all (`displayCutout`, `safeDrawing`, `safeGestures` and `safeContent` appeared zero times; the nineteen `WindowInsets` hits were scattered usages). The example starts from what the `safe*` insets actually are: not measurements but unions, read straight out of the `WindowInsetsHolder` constructor bytecode of foundation-layout 1.11.4 — `safeDrawing = systemBars ∪ ime ∪ displayCutout`, `safeGestures = tappableElement ∪ mandatorySystemGestures ∪ systemGestures ∪ waterfall`, `safeContent = safeDrawing ∪ safeGestures`, which is where the first trap falls out: **waterfall is not part of safeDrawing**. A device measurement (SM-A725F / Android 13, 1080x2400 @450dpi) then separates the device from the window: the phone does have a punch-hole cutout (`boundingRect=Rect(514, 0 - 566, 86)` per `dumpsys`), yet with `decorFitsSystemWindows=true` every one of the thirteen insets Compose reports is **zero**, status bars included, because the decor has already cut them away. The screen therefore lets you flip `layoutInDisplayCutoutMode` and edge-to-edge in place, and the same device then reports statusBars 0/86/0/0, safeDrawing 0/86/0/135 and safeGestures 0/120/0/135 — the gesture inset being the taller one is why their union, safeContent, follows 120 rather than 86. `WindowInsets.cutoutPath` (new in Compose 1.11; absent in 1.8.2) comes back as `Rect.fromLTRB(514, 0, 566, 86)`, matching the platform bounding rect exactly, and is null until the window opts in. The `displayShape` card corrects an assumption rather than confirming one: it is not API 34-only — core 1.18.0 synthesises a rounded rectangle from `Display.getRealSize()` plus the four `DisplayCompat.getRoundedCorner()` radii (all 90px here), so an API 33 device returns a non-empty path that the platform never provided, and support cannot be judged by a null check because the fallback is `DisplayShapeCompat.EMPTY`, whose `getPath()` hands back a fresh empty Path. Two traps came out of building the screen itself, both caught on the device: a `DisposableEffect` that restored window state was placed inside a list card, and a 40-row measurement showed `onDispose` firing the moment the item scrolls off screen rather than when the screen closes, so the state moved up to the screen root; and the idiomatic `when (this) { is Activity -> ... }` context walk compiles to a JDK 21 `SwitchBootstraps.typeSwitch` invokedynamic that the HotSwan 2.0.0 interpreter in debug builds does not implement, which did not crash but silently emptied the composition (semantics root at 0x0) until it was replaced with `LocalActivity.current`.
  - Sensor-Fusion Compass — the project's first use of the sensor stack (`SensorManager` appeared zero times before this example). Subscribes a single fused `TYPE_ROTATION_VECTOR` sensor and walks the four-step azimuth pipeline (`onSensorChanged` → `getRotationMatrixFromVector`, which returns `void` rather than a success boolean → `remapCoordinateSystem` → `getOrientation`, whose `orientation[0]` is radians in -π..π and needs 0-360 normalisation), contrasting it in a table with the accelerometer + magnetometer pairing it replaces and with `TYPE_GAME_ROTATION_VECTOR`, which drops the magnetometer and therefore has no north reference at all. A device measurement (SM-A725F / Android 13, qualcomm "Rotation Vector Non-wakeup") settled one implementation detail rather than leaving it to a defensive guess: `event.values` arrives with **5** elements, not the 3-4 the rotation vector is defined as, but passing that full array to `getRotationMatrixFromVector` raises nothing and yields a rotation matrix identical to one built from a `copyOf(4)` copy, so the truncation was removed rather than allocating a new array on every event. The display-rotation card reads the live `Surface.ROTATION_*` value through `ContextCompat.getDisplayOrDefault(context).rotation` — chosen over the deprecated `WindowManager.defaultDisplay` so the file stays warning-free on minSdk 24 — keyed on `LocalConfiguration` so rotating the device recomputes the axis mapping on screen. The centrepiece is a deterministic wrap-around demo that needs no sensor and therefore runs on an emulator: feeding the eight-step sequence 348° → 15° through the textbook `previous + α × (raw − previous)` low-pass ends at 118.7° — the opposite side of the dial — because the subtraction crosses 359°/0° and produces −356, while normalising the delta to -180..180 first (`((raw - previous + 540) % 360) - 180`) tracks it to 4.8°; both series are computed live and shown step by step next to two needles. The shimmer overlay reuses the element's own already-measured `DrawScope.size` instead of a hand-matched parallel tree, made visible in the demo card where two profile-row texts of different lengths ("김코틀린" vs "Compose 개발자") each get a shimmer bar auto-sized to their own width. Crossfade independence comes from modifier ordering: `drawWithContent` (outer) draws the real content — wrapped by the inner `graphicsLayer { alpha = contentAlpha.value }` — then draws the shimmer rectangle directly, outside that alpha, so content and shimmer fade on separate curves; reversing the two would fade the shimmer along with the content. Three mechanism findings come from reading coil 3.1.0 bytecode rather than docs: (a) `coil3.compose.internal.UtilsKt.previewHandler` consumes `LocalInspectionMode` first and only reads `LocalAsyncImagePreviewHandler` when it is true, so the handler has zero effect during ordinary app runs and `@Preview`/screenshot runners are what turn it on; (b) enabling inspection mode alone changes nothing, because the default `AsyncImagePreviewHandler.Default` still calls `ImageLoader.execute()` — both CompositionLocals must be provided together; (c) the one-line factory `AsyncImagePreviewHandler { image }` wraps the image in `AsyncImagePainter.State.Loading(painter)`, **not** `State.Success`, so the pixels are fixed while any wait-for-Success logic never completes — surfaced directly by the demo's state label instead of being hidden, and re-confirmed at runtime by a throwaway instrumented test on a real device (SM-A725F/API 33) that recorded `emitted=[Loading]` with no `Success` at all. `AsyncImagePreviewHandler`/`LocalAsyncImagePreviewHandler` carry `@ExperimentalCoilApi`, so the handler declaration is `@OptIn`-annotated. Runs on the project's existing coil3 3.1.0 with no dependency change; the `coil-test` `FakeImageLoaderEngine` + `SingletonImageLoader.setUnsafe()` route is shown as a code snippet only, matching how the sibling example presents Paparazzi/Roborazzi
